# Direct WSS gateway — Meshtastic 2.7.15

This branch stays on the existing `custom-2.7.15` base. Neither Meshtastic nor
ESP32 SDK dependencies are upgraded. The gateway uses `AUTH_GATEWAY`, not
MQTT, to communicate with MVT_Relay.

## Build and configure

```powershell
platformio run -e heltec-v3
```

The existing Heltec V3 environment enables `HAS_MVT_WSS_GATEWAY=1` and excludes
MQTT/WebServer. Configure its existing MQTT settings through the Meshtastic
client (they are reused for WSS, no broker is started):

- `enabled`: enable the direct gateway.
- `username`: Room ID of an already created portal room.
- `password`: that room's Relay Key.
- `address`: empty for `wss://movetain.app/ws`, or a full `wss://host/ws` URL.

Only encrypted `wss://` connections are accepted. The server certificate and
hostname are verified against the included ISRG Root X1 certificate, downloaded
from `https://letsencrypt.org/certs/isrgrootx1.pem`. A separately hosted portal
using a different CA needs its corresponding root certificate in `MvtRootCA.h`.
WiFi NTP/GPS must provide system time for TLS certificate validity checks; the
Relay heartbeat ACK additionally supplies the clock used for portal events.

A rejected key, missing/blocked room or replacement by another gateway stops
reconnection. Change the credentials or disable/enable the gateway to retry.
A normal network loss reconnects automatically and replays cached data only
following `AUTH_GATEWAY_SUCCESS`.

## Supported room gateway protocol

| Portal command/event | Gateway behavior |
| --- | --- |
| `AUTH_GATEWAY_SUCCESS` | Start authenticated session and replay node/waypoint state |
| `GATEWAY_HEARTBEAT_ACK` | Synchronize Unix time; heartbeat every 15 seconds |
| `CMD_TX_LORA_CHAT` | MV binary port 256, correct recipient/channel/packet ID/SOS and sender |
| `CMD_TX_LORA_WAYPOINT` | MV binary point/target, correct recipient, coordinates, comment, altitude |
| `WAYPOINT_DELETED` | Remove cached point and queued attachments; no replay resurrection |
| `CMD_REFRESH_GATEWAY` | Current gateway telemetry and state refresh |
| `CMD_PING_NODE` | Correlated device telemetry request, or fresh MV beacon for a virtual node |
| `CMD_POLL_ENV` | Correlated environment telemetry request |
| `CMD_TRACEROUTE` | Actual RouteDiscovery request and measured route/SNR response |
| `ERROR` / administrative close | Handle authentication failure, replacement and restriction |

Incoming ordinary Meshtastic text, position, user information, device/environment/
air-quality/health telemetry and waypoint packets are bridged. MV beacons, chat,
SOS, target points, beacon stop, optional altitude and heart rate are decoded.
Native and virtual node keys are distinct (`!xxxxxxxx` / `!xxxxxxxx_mv`).

Delivery statuses are `SENT` for broadcast dispatch, `AWAITING_ACK` for a direct
message, `DELIVERED` only for a routing ACK from the intended recipient with
matching request ID and destination, `FAILED` for an explicit error, and
`UNCONFIRMED` for an ACK timeout. Late recipient ACKs can recover the status for
10 minutes. A relay or gateway's own success is never delivery proof.

Radio frames are limited to 233 bytes. Oversized UTF-8 is rejected rather than
silently truncated. JSON is serialized/parsed using cJSON. WebSocket SDK buffer
chunks are assembled before parsing, control frames are excluded and malformed/
oversized frames fail closed. Mesh commands run on the cooperative mesh thread;
WebSocket callbacks only enqueue input.

Replay is bounded in RAM: 96 node records, 64 points, 32 unsent events, 16 active
requests and 64 late ACK records. Standard nodes are also rebuilt from NodeDB.
The oldest buffered event is dropped with a warning on overflow. These buffers
survive a connection loss, not a reboot. Replay uses incremental `NODE_UPDATE`
messages so a partial local cache cannot erase existing portal tracks/nodes.
Track recording remains server-side and receives the corrected Unix timestamps.
The separate Android `phone_sync` role (photos and phone cloud files) is not a
radio gateway protocol and remains provided by the Android app.

## Verification

Compared with MVT_Relay commit `dc0be624671686b239cd39c0977925a08591f62e`
(13 October 2026). Host tests compile the actual `MvtWssGateway.cpp` with
radio/socket adapters, actual generated **2.7.15** protobuf types and nanopb,
and cJSON. They check address/ID/channel, escaping/UTF-8, deduplication, recipient
ACK binding, wrong/late ACK, timeout, radio failure, correlated diagnostics,
traceroute SNR, MV data, offline replay, point deletion, chunked input and gateway
replacement. Golden MV bytes are generated by the current portal's encoder.
The integration test runs that Relay's real WebSocket server against isolated
storage with mock signed authentication, never a production room.

For Windows host tests, place Zig 0.13.0 in `.tools/`, cJSON 1.7.19 source/header
in `.tools/cjson/`, install Node.js and Python, and run a PlatformIO build first
(to populate the pinned nanopb dependency). With a checkout of the current Relay:

```powershell
python tests/wss/run.py --zig .tools/zig-windows-x86_64-0.13.0/zig.exe --relay ../
```

Compilation logs, vectors and actual firmware events are stored under
`.tools/wss-tests/`, which is ignored by Git. Real radio range, WiFi/TLS on the
physical board and end-to-end LoRa delivery still require a hardware run.
