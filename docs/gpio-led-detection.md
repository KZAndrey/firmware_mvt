# 2.7.15.GPIO_2 — GPIO LED и Detection Sensor

Эта ветка предназначена **только для GPIO LED на nRF52840 Pro Micro DIY с TCXO** (`nrf52_promicro_diy_tcxo`). Это не WSS-прошивка Heltec и не обновление MQTT-шлюза WiFi-Gateway / GTW.

## Зачем нужна доработка

MOVETAIN Equipment использует отдельный канал `gpio` для управления Remote Hardware. Мы добавляем датчик движения, сохраняя публичный канал основным: обычные сообщения ноды не должны менять канал из-за подключения датчика.
В исходной базе 2.7.15 Detection Sensor отправляет события и периодические отчёты через основной канал. Отправка блокируется при стандартном имени канала и стандартном ключе AQ==. Приложение может разрешить включение модуля без предупреждения об этом ограничении.
Чтобы использовать штатную реализацию, пришлось бы менять основной канал. В этой сборке вместо перестановки каналов Detection Sensor явно выбирает существующий `gpio`.

## Что изменено

- Remote Hardware включён только для выбранной платы (как в предыдущей сборке GPIO LED).
- Флаг `MOVETAIN_DETECTION_GPIO_CHANNEL` включён только для `nrf52_promicro_diy_tcxo`.
- И сообщения обнаружения, и периодические отчёты состояния отправляются через включённый канал с именем `gpio`, без учёта регистра.
- Номер слота не фиксирован. Основной публичный канал можно оставить прежним.
- Если gpio отсутствует или выключен, отправки нет; в последовательном журнале появляется ошибка. Нет незаметного перехода на основной канал.
- Используется PSK настроенного канала. Это не PKI и не новый формат шифрования.
- Формат события остаётся стандартным Meshtastic: порт 10 DETECTION_SENSOR_APP, текст `имя detected` либо `имя state: 0/1`; необязательный символ bell сохранён.
- Другие платы без указанного флага сохраняют штатное поведение.
- Версия устройства отображается точно как `2.7.15.GPIO_2`. Поле custom в version.properties задаёт полную версию; короткая базовая версия остаётся 2.7.15.

## Как настроить в приложении Meshtastic

1. Оставить основной публичный канал и текущие RF-настройки.
2. Добавить/сохранить включённый канал `gpio` с общим PSK оборудования. Ключи не публиковать в Git или документации.
3. В Detection Sensor включить модуль, задать имя и GPIO подключённого датчика.
4. Для цифрового датчика с активным HIGH: EITHER_EDGE_ACTIVE_HIGH для обоих переходов; подтяжку выключить, если выход датчика сам формирует уровень.
5. Выбрать минимальный интервал отправки и ненулевой интервал состояния. Последний — самостоятельная периодическая отправка нодой, а не опрос с портала.
6. Удалить этот GPIO из available_pins Remote Hardware: READ_GPIOS в этой базе меняет режим входа на INPUT_PULLUP и может влиять на датчик.

Текущая тестовая GPIO LED: BLUE LED — GPIO8 OUTPUT, RED LED — GPIO24 OUTPUT, TOUCH — GPIO20 INPUT, движение — GPIO22 Detection Sensor. Имя датчика `Dvizh`, минимум 15 секунд, периодическое состояние 900 секунд, оба перехода с активным HIGH. Эти параметры хранятся в настройках устройства, не зашиты в бинарник.

## Доставка в MOVETAIN

GPIO LED → обычная радиосеть Meshtastic → MQTT-шлюз → портал.
Промежуточным нодам не нужны модуль датчика и ключ для ретрансляции. Нужны совместимые частота/пресет и разрешённая ретрансляция.
MQTT-шлюзу нужны соответствующий канал/PSK, uplink, разрешение пересылать исходный трафик и подключение к брокеру комнаты. Включать Detection Sensor на самом шлюзе для MQTT-пересылки не нужно. Публичный брокер Meshtastic фильтрует такие события.
Портал сопоставляет ID радионоды и имя датчика. В пакете нет номера GPIO; его берём из проверенной конфигурации карточки. Один модуль Detection Sensor на ноду.
Карточка показывает последнее полученное состояние и местное время приёма. Храним только последнее состояние, без бесконечного журнала событий. Сохранение карточки не настраивает физическую ноду.

## Ограничения

- READ/WATCH/WRITE Remote Hardware для датчика не используются. Запрос состояния по требованию не добавлен.
- Минимальный интервал ограничивает наблюдение/передачу: короткие изменения могут быть пропущены. Это не гарантированная система охраны или аварийной защиты.
- Последнее полученное состояние не доказывает текущее состояние и доступность ноды.
- PSK-шифрование этой базы не предоставляет криптографическую проверку целостности или долговременную защиту от повтора. Нельзя считать сообщение доказательством личности отправителя.
- Установка штатной прошивки возвращает штатную маршрутизацию через основной канал.
- Первый этап портала — MQTT. Эта ветка сама по себе не добавляет поддержку оборудования в WSS/Phone Gateway.

## Проверки и сборка

`python tests/test_detection_gpio_channel.py <host C++ compiler> [аргументы]` компилирует реальные методы отправки с подставной радиослужбой: отсутствующий/выключенный gpio, выбор вторичного канала, регистр имени, обнаружение, оба состояния и bell. Полная сборка PlatformIO также обязательна.
`python bin/buildinfo.py long` должен вернуть 2.7.15.GPIO_2.
Обычная сборка: `pio run -e nrf52_promicro_diy_tcxo`. Локальный detection-local.ini использует уже скачанные пакеты и не включается в Git.
В портале тестируются зашифрованные пакеты, неверные ключи/порты/адреса, конфликты GPIO, сохранение/удаление последнего состояния, дедупликация, права доступа и UI конструктора.

## Артефакты и обновление

UF2/ZIP, логи, резервные копии настроек и локальные инструменты не коммитить. Хранить локально в release/ или .tools/, для публикации использовать release assets. В Git — исходники, тесты и пояснения.
Перед прошивкой проверять ID и модель ноды, сохранять настройки локально. После обновления читать версию, проверять каналы/ключи, RF-настройки и модули. Сборка, публикация и фактическая установка — разные результаты.
Не менять WSS-прошивку и не перепрошивать WiFi-Gateway / GTW в рамках этой работы.
